## Workload and boundary

One owner and project are bootstrapped before conversation metering. Each case
creates one conversation, sends three 36–45-character visitor messages and two
37-character owner replies (200 content characters total), uploads and downloads
one exact 1,048,576-byte ASCII attachment, reads the final five-message transcript,
opens a socket which replays four messages, disconnects, sends the fifth message,
reconnects after the previous cursor, and sends one application-level ping. Six
frames arrive: five committed messages and one pong. No project dashboard socket
is opened; the shared project object's broadcasts are nevertheless counted.

The new-visitor case includes widget session/contact creation. The returning case
reuses its still-valid visitor token; it does not simulate an expired session,
new browser, identity verification, or a fresh widget-session request. These are
two observations on a small local database, not statistical load benchmarks.
The attachment is synthetic workload input, not a provider response. The wrapper
calls the actual emitted application and real local bindings without changing
application admission or storage behavior. Its outbound fetch is disabled; no
provider credentials are inherited. No email, payment, inference, deployment or
remote database operation is performed.

## Setup, assets and background

Bootstrap plus project lookup cost two dynamic requests, eight D1 statements,
with a known subset of 18 read / 16 written rows and two missing metadata results.
These are installation setup, excluded from recurring conversation units.
Migration application and the readiness health probe are also excluded.

One direct `/widget.js` request returned 964,207 bytes through static assets and
made no measured Worker invocation. This is one asset observation, not an entire
browser/dashboard network budget. Static requests are separate from dynamic
requests; caching policy and ancillary asset services require their own estimate.

A scheduled drain after the two conversations made 63 D1 statements (25 exposing
98 read / 10 written rows; totals unknown) and four DO fetches: one conversation
and one project broadcast per conversation. The next idle tick made 21 D1
statements exposing 37 read / 0 written rows, no DO calls and no queue messages.
The scenario apportions the four recovery fetches as two per conversation.
At this small retained dataset, 43,200 idle ticks imply 1,598,400 locally observed
idle read rows/month **before** incremental recovery and dataset growth; this
is a conditional extrapolation, not a hosted row budget. Recovery scans, pruning,
knowledge refresh, integrations, training and other enabled background work can
change it. No such workload was configured here.

Formula: **monthly units = fixed background + measured units/conversation × V**.
Use 43,200 minutely ticks in a 30-day month when cron is enabled. The conservative
visitor mix below is 100% new visitors. Returning valid-token conversations save
one dynamic request each. DO request equivalents are `(12 + 2 + 1/20) × V`,
including apportioned recovery; no duration is inferred from local wall time.

R2 assumes **steady-state, owner-managed 30-day retention**, one 1 MiB object per
conversation, no knowledge corpus/imports/other objects and constant occupancy
`V × 1,048,576 / 1e9` GB-month. This is a scenario, **not a shipped automatic
30-day deletion policy**. Without deletion storage accumulates across months.
The initial filling month and nonuniform traffic have different average daily
peaks. Cleanup's additional D1/Worker work is excluded and unmeasured.

## Limits actually checked

`node --test tests/usage-limits.mjs` runs real application/D1/DO/R2 admission with
`widgetSessionsPerIpHour: 2`, `repliesPerProject: 2` and
`repliesPerInstallation: 3`. Two sessions return 201; the third returns 429 with
positive `Retry-After`. Two automatic reply admissions in one project are queued;
the third message persists but its reply is terminally failed for the project
ceiling. Repeated explicit requests return 429 with `Retry-After` and retain one
failed command. Another project admits one reply, then fails on the installation
ceiling. There are zero provider attempts, usage rows and outbound calls. An inert
test key satisfies configuration admission only; the queue deliberately has no
consumer and no provider output is fabricated. This proves admission guards,
not provider execution, spend accounting, queue throughput or hosted capacity.

Shipped defaults remain 30 widget sessions/IP/hour, 5,000 sessions and
conversations/project/hour, 15 messages/conversation/minute and 120/contact/hour;
AI defaults are 200 automatic replies/project/day, 2,000/installation/day,
estimated $10/project/day and 500 context runs/project/day. All are configurable
through `RATE_LIMITS` / `AI_DAILY_CEILINGS` (see `docs/PUBLIC-LIMITS.md`). The count
defaults permit at most 6,000/project and 60,000/installation automatic replies
in 30 days before another guard intervenes. This is a guard, not measured
throughput or a product tier. Spend is based on reported completed usage and can
be exceeded by work already in flight. This run does not exercise the spend or
context-run ceiling and makes no capacity claim.

## Reproduce

Use Node >=26.8.1 and pnpm 10.12.4. From the repository:

```sh
node scripts/operations.mjs describe
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 pnpm install --frozen-lockfile
pnpm run build
node scripts/usage/measure.mjs
node scripts/usage/summarize.mjs .wrangler/usage/run-<id>/measurement.json
node --test tests/usage-summary.mjs tests/usage-limits.mjs
```

The opt-in meter defaults to localhost 8784/8785, retains isolated raw logs/state
under ignored `.wrangler/usage/`, and stops its server on completion/failure.
`H2H_USAGE_OUTPUT` chooses another evidence directory. The guard test uses
8786/8787 and disposes its runtime. No product package entry or deployment
configuration selects the wrapper. It must never be deployed. Persisted local
state includes synthetic authentication state; publish the sanitized measurement,
not the state database. Runtime logs/raw state for this run were retained under
`/Users/zemaj/.orchestrator/evidence/runeditrun/h2h-usage-execution/run-KsCpEq/`;
that directory is external evidence, not part of the release.
